# 达人广场「邀约带货」两段式批量（tools/creator_invite）

在巨量百应「达人广场」给一批抖音达人发「邀约带货」卡片，分两段：

1. **plan（只读，什么都不发）**：找人、查状态、配话术和商品，出一份清单给人看。
2. **run（要用户对这一份清单明确同意）**：只发清单里的人，一位一位发，发一位记一位。

工具只调两个命令行，自己不碰平台：
- 聚水潭 `jushuitan-engineering`（`node bin/jst.mjs`）：`find` 找达人、`lookup` 按抖音号查一位（抖音那边找到的人用它补数据）；配置了 `min_stock` 时还用 `goods-detail` 查真实可用库存。
- 抖音 `douyin-engineering`（`node bin/dy.mjs`）：`buyin author-invite-status` 一次查一批达人的邀约状态，`buyin author-invite` 预览 / 发送一张邀约卡。
  要用带 `--commission-rate` 和 `author-invite-status` 的版本（douyin-engineering 的分支 `author-invite-commission`，2026-10-29 已并入它的本地 main）。

只用 Python 标准库，macOS 自带的 `/usr/bin/python3`（3.9）就能跑。只在 Mac 上用：台账加锁用的是 `fcntl`。

## 准备

- 调试 Chrome（默认 `http://127.0.0.1:9222`）里登录了**百应**和**聚水潭**，并且**开着一个百应的标签页**。工具给抖音命令行加 `--no-open`，不会替你开新标签页。
- 一份配置（JSON），照 `config.example.json` 写，放在仓库外、权限 600。店铺 ID、聚水潭子账号、邀约卡上的微信号只写在那份里。

| 配置 | 意思 | 默认 |
|---|---|---|
| `dy_expect_shop_id` | 抖店店铺 ID：每条抖音命令都先核对登录的是不是这家店（不是就退出码 79） | 必填 |
| `jst_expect_uid` | 聚水潭子账号：每条聚水潭命令都先核对（本地核对令牌，不发请求） | 必填 |
| `invite_wechat` / `invite_phone` | 邀约卡上给达人看的联系方式，格式照抽屉的规则；至少一个 | — |
| `brand` | 话术里 `{品牌}` 换成什么 | 话术里有 `{品牌}` 就必填 |
| `commission_rate` | 卡上的专属佣金：0 = 不开（卡只为让达人加微信，佣金到微信里谈，用户 2026-10-29 下午）；1 到 25 = 卡一发出去平台就开这个比例的长期专属佣金（这时 `rights` 要有 `high-commission`） | 0 |
| `rights` | 权益：`high-commission`（专属高佣）、`free-sample`（免费申样）、`video-material`（视频素材支持）、`video-boost`（优质视频投放）；可以一个都不勾；`high-commission` 和 `commission_rate` 要一起有、一起没有 | 只有免费申样（2026-10-29 下午） |
| `products` | 1 到 5 款（一张卡最多 5 款）：`{id 抖音商品 ID, name, price 售价（元）, styles 聚水潭款号}`；`styles` 只在 `min_stock` 大于 0 时必填 | 必填 |
| `min_stock` | 0 = 不看库存，能挂上卡的都配（老板 2026-10-29）；大于 0 时，一款的真实可用库存（各款号加起来）低于它就不配 | 0 |
| `find` | 找达人的条件：`goods_category`（帽子 1000003461，以后可以换中高端女装的类目）、`price_min` / `price_max`（件单价）、`queries`（几组粉丝范围，每组 `pages` 页，每页 20 位；每组还可以写 `level_min` / `level_max`、`sales_min` / `sales_max`，交给平台先筛）；`dy_queries`（抖音那边也找：每组 `{"args": ["buyin", "authors-…", "--筛选=值", …]}`，原样交给抖音命令行的只读找达人命令，只许写筛选和页数）、`dy_lookup_max`（抖音那边找到的新人一次最多到聚水潭查几位，默认 60） | 见下 |
| `rules` | 分类、不进清单和标记的门槛（见下「本地先筛」和「三类」）；`drop_ids` 一定不要的抖音号、`keep_ids` 不按「自己牌子」「骗样」两组规则去掉的抖音号 | 见下 |
| `templates` | 三类话术，`small` / `mid` / `big`；不写就用内置的三条 | 内置 |
| `weekly_cap` / `daily_cap` | 我们自己每周 / 每天最多发几位；`daily_cap` 0 = 不限（2026-10-29 先加了每天 20，同天用户说去掉：发不发用户说了算，节奏靠 `wait_between`） | 800 / 0 |
| `quota_margin` | 平台本周额度剩下不到这么多就停 | 50 |
| `gap_seconds` | 任意两次平台请求之间至少隔几秒（不能小于 3） | 3 |
| `wait_between` | 发两位之间随机等多少秒（正式配置 2026-10-29 起用 [180, 300]：3～5 分钟一位） | [15, 30] |
| `plan_max_age_days` | 清单多少天后作废、要重新 plan（按天分批发一份大清单时放到 7） | 3 |
| `send_order` | 发的先后：`category` 照清单顺序（小达人、中大博主、专场型）；`mixed` 三类轮流、每类里最合适的先发——每天按 `daily_cap` 发一批时，每批都是剩下里最合适的（2026-10-29：合适的都留作候选，按天来发） | category |
| `follow_hours` / `follow_days` / `follow_max` | follow：北京时间几点到几点查 / 发卡后跟几天 / 一次最多查几位 | [9, 23] / 14 / 40 |
| `home` | 台账和清单的默认位置 | `~/.claude-relay/platform/creator-invites` |

## 第一段：plan

```bash
/usr/bin/python3 tools/creator_invite/invite.py plan --config <配置> --count 30 [--out-dir <目录>] [--ledger-dir <目录>]
```

做的事（全是只读命令，没有一条带 `--execute`）：

1. 只有 `min_stock` 大于 0 时：每款商品的每个款号 `jst goods-detail`，加起来是这款的真实可用库存，低于 `min_stock` 的不配。默认 0，不看库存、一个请求都不发。
2. 两边都找（用户 2026-10-29）：聚水潭——每组 `queries` 跑一次 `jst find --platform DY --goods-category … --price-min … --price-max … --not-added`（带粉丝范围、页数）；抖音——每组 `dy_queries` 跑一次百应达人广场的只读搜索（工具补上 `--expect-shop-id`、`--no-open`），聚水潭那边已经找到的记成「两边都有」，新的每位到聚水潭按抖音号查一次（`jst lookup`，最多 `dy_lookup_max` 位），拿到和 `jst find` 一样的数据（粉丝画像、近 30 天带货品类和销售额），这样两边的人走下面同一套规则；百应行上的按钮已经不是「邀约带货」（本店沟通过、禁用）的、已在本店百应达人库里的不查也不进，聚水潭查不到的、已经在聚水潭「我的达人」里（有人在跟）的、件单价不在 `price_min`～`price_max` 的不进；查的时候聚水潭限流就不再往下查，已经查到的照常进清单，清单里写着后面几位没查。抖音那边的搜索用 douyin-engineering 的 `buyin authors-square`（2026-10-29 起能按达人广场自己的筛选找、能翻页：`--category`、`--fans-min/--fans-max`、`--level-min`、`--fans-gender`、`--settle30d-min`、`--filter 字段=值`、`--pages`）。清单的每一行都写着来源（聚水潭 / 抖音 / 两边都有）。默认两组都让平台先筛掉带货等级低于 LV2 的，小达人那组再筛掉近 30 天销售额不到 1 万的（20 万粉以上不按销售额筛：销售额不公开的大主播会被平台整个筛掉）。
3. 本地先筛：抖音号格式命令行不收的、台账里邀约过的（或不知道上次发出去没有的）去掉；**帽子占比 ≥ 90% 的标「疑似同行自播号」，默认不进清单，单独列一张表**；**女性粉丝低于 60% 的不进**（我们卖女帽，用户 2026-10-29；粉丝画像只给占比最大的性别：「男性 62%」算女性 38%）；粉丝不到 5000 的不进；`rules.drop_ids` 里的不进。
   **专门带自己牌子的不进**（用户 2026-10-29）：名字像店铺 / 品牌号（`own_brand_words`：女装、男装、服饰、服装、羽绒、皮草、大码、工厂、档口、老板娘、旗舰、官方、店、品牌、定制、高定、上新……），或者这次找到的人里有 ≥ `matrix_min`（2）个号用同一个店名开头（「小鹿（…）」「木子-…」这种店铺矩阵号；店名是昵称里第一个括号、点、横线、竖线、空格前面那段，英文不分大小写）。
   **可能骗样品自己用的不进**（用户 2026-10-29）：带货等级低于 LV2（`min_level`）；近 30 天销售额区间下限不到 1 万元（`min_sales30d`）；销售额不公开（「无数据」）而且等级低于 LV3（`hidden_sales_min_level`）；粉丝 5 万以上（`sales_per_fan_from`）、销售额下限 ÷ 粉丝数不到 0.2 元（`min_sales_per_fan`，粉多卖少）。
   这两组规则是按名字和销售数据猜的，清单里各有一张表写着每位的原因；要留下哪位，把抖音号写进 `rules.keep_ids`。准确的做法是看她合作过几家店（百应「达人合作店铺」），抖音命令行还没有这条读命令。
   进清单但标出来给人看的：帽子占比不到 1% 的、粉丝性别不知道的、帽子占比 ≥ 50%（`own_hat_flag`，可能自己做帽子）的、近 30 天一类别的货占 ≥ 90%（`single_category_flag`，可能只带一个牌子）的。
4. 剩下的排个先后：每一类里没有标记的在前、帽子占比高的在前，打平时聚水潭和抖音两条路线轮流（不然先找到的那边会把名单占满），三类轮流（大主播/专场型、中大博主、小达人、大主播……），这样清单够数时三类都有。按这个顺序每 20 位跑一次 `dy buyin author-invite-status`：搜不到的、状态不是 1（「邀约带货」）的去掉；够 `--count` 位就不再查，查过、能邀、但超出人数的列为「备选」。浮层里本周的次数（按达人等级分档）记进清单。
5. 分三类、配商品和话术，写三个文件（权限 600）：`plan-<编号>.md`（给人看）、`.csv`（同样的列，Excel 能开）、`.json`（给第二段用）。

**三类**（按 `jst find` 给的字段，先判第一条）：
- **大主播 / 专场型**：按销售额定的主播类型是直播（`channelBySales`），近 30 天直播销售额区间下限 ≥ 500 万（`sales30dLive.min`），带货等级 ≥ LV4。
- **中大博主**：粉丝 ≥ 20 万。
- **小达人**（垂类穿搭 / 配饰）：粉丝 5000 到 20 万（15 万～20 万也算小达人，用户 2026-10-29）。

**配商品**：配置里的商品每位都配（最多 5 款，一张卡的上限）：主推是售价最接近这位达人件单价的那款（一样近取配置里靠前的），其余的按配置顺序附带。设了 `min_stock` 时缺货的不配。

**话术**（内置，`{品牌}` 换成配置里的 `brand`；字数照抖音命令行的算法，都在 150 字以内；只写「包邮」，不写快递公司，写了配置检查就不过）：
- 小达人：您好！我们是原创设计师帽饰品牌{品牌}，主打英伦复古、老钱风女帽，客单价高、转化好。很喜欢您的穿搭内容，诚邀您带我们的帽子，免费寄样包邮。合作细节加微信详聊，期待合作～
- 中大博主：您好！我们是设计师女帽品牌{品牌}（英伦复古/老钱风），一直关注您的内容，诚邀您合作带货：现货样品任选3顶，免费包邮寄出。合作细节加微信详聊，期待您的回复～
- 大主播 / 专场型：您好！我们是设计师女帽品牌{品牌}，主打英伦复古、老钱风全系帽饰。诚邀您做一场品牌专场：专场样品看中多少款寄多少款，全系现货锁库存，优质视频投流支持。合作细节加微信详聊，期待合作！

**卡片（2026-10-29 下午起）**：不开专属佣金、不勾专属高佣——卡只为让达人加微信，佣金到微信里谈（用户 2026-10-29 下午），寄样签收后开专属佣金那一路照常起草、批准了才开；权益只勾「免费申样」（用户：可以勾），不勾视频素材支持、优质视频投放。注意：这几款在精选联盟里没开免费申样，卡上的商品照样显示「买样」，抖音命令行预览会提醒，工具把每款按什么发（`samples`）和提醒（`warnings`）记进台账和执行记录；要卡上也显示免费，得在百应把这几款的样品设置改成免费申样。话术里不提佣金，「免费寄样包邮」写在话术里，达人回复后走聚水潭寄样单。以前（2026-10-29 上午）卡上勾专属高佣、开 25% 长期专属佣金，那 5 位的卡发出去时平台已经给她们开好了。

## 第二段：run

```bash
/usr/bin/python3 tools/creator_invite/invite.py run --config <配置> --plan <plan-编号.json> --confirm <编号> [--limit N] [--only <抖音号,…|@文件>] [--ledger-dir <目录>]
```

- `--only`：这次只发清单里用户挑的那几位（抖音号用逗号分开，或 `@文件` 每行一个），照发的先后；写了清单上没有的号就不发、退出码 2。
- `--confirm` 必须写**这份清单的编号**（用户同意的是哪一份就写哪一份）；编号不对、清单超过 `plan_max_age_days`、清单里的专属佣金或权益和现在的配置不一样，都不发、退出码 2。
- 只发清单里的人，按清单顺序。每一位：
  1. 先跑一次**不带** `--execute` 的 `dy buyin author-invite`（预览）。只有预览说状态 1、门槛 -1（不弹确认）、没被拦的才往下走，其余记一笔「跳过」。
  2. 读预览里本周的次数（`statusBefore.weeklyQuota`）：剩下的不到 `quota_margin` 就**停**。
  3. 台账里先写一行 `attempt`（落盘后才往下），再带 `--expect-status 1 --expect-popwindow -1 --execute` 发送：预览和执行绑在一起，这期间状态或门槛变了，命令行就 `STATE_CONFLICT`、什么都不发。
  4. 台账里写一行 `result`。
- 两位之间随机等 15～30 秒（`wait_between`）；任意两次平台请求之间至少 3 秒。
- 一台 Mac 上同一个台账同时只能有一个 run（`invites.lock`）。

**什么时候停**（停下时打印停在清单第几位、为什么，执行记录写在台账目录的 `run-<时间>/report.md`）：

| 情况 | 怎么办 |
|---|---|
| 退出码 76（验证码 / 限流）、77（登录失效）、79（登录的不是这家店）——预览或发送时 | 立刻停，不再发任何请求；到调试 Chrome 里处理好再重跑 |
| 抖音命令行说 `[IDENTITY_UNVERIFIABLE]`（核对不了登录的是哪家店；2026-10-29 真遇到过：百应掉登录，`getUser` 给的店铺号是 0）——plan、预览或发送时 | 立刻停，提示到调试 Chrome 里重新登录百应。命令行是在发卡之前核对的，这位**没发出去**，重跑会再发她 |
| 平台本周额度剩下不到 `quota_margin` | 停 |
| 我们自己本周已发（台账）到了 `weekly_cap`，或今天已发到了 `daily_cap` | 停（周一 0 点 / 每天 0 点按北京时间重新算）；明天同一个命令接着发 |
| 清单出了以后又写进 `rules.drop_ids` 的人 | 跳过，一个请求都不发 |
| 发送超时、被打断（130）、没拿到结果 | 停；这位记为「不知道发出去没有」，**以后也不会再发**，到百应 › 消息里看 |
| 连续 3 位预览失败 | 停，查原因 |
| `STATE_CONFLICT` | 跳过这位、继续；什么都没发，以后的 plan 会重新查她 |
| `--limit` 到了 | 停 |

**接着上次停下的地方**：同一个命令重跑就行。台账里有 `attempt`、又没有「没发出去」的 `result` 的抖音号，永远不再发——哪怕进程在写完 `attempt` 之后死掉。

## 第三段：follow（达人回没回，在这台 Mac 上弹通知）

```bash
/usr/bin/python3 tools/creator_invite/invite.py follow --config <配置> [--ledger-dir <目录>] [--no-notify]
```

用户 2026-10-29：「达人要我们加她微信，我能及时看到吗」→ 在 Mac 上弹通知。只读，不读也不发私信：

- 查谁：台账里发出去了的卡（`sent: true`），发卡后 `follow_days` 天内、还没回也没拒的。发卡 2 天内的隔 25 分钟以上查一次，更早的隔 115 分钟以上；一次最多 `follow_max` 位，最久没查的先查。北京时间 `follow_hours` 之外不查。
- 怎么查：`dy buyin author-invite-status --aweme-id=… --names`（每位一次搜索 + 每 20 位一次状态读，请求之间至少 4 秒，和 run 共用一个请求钟）。
- 按钮从 2「继续沟通 · 待回复」变成 4「已建联」（她回了）→ 弹「百应：达人回复了邀约」，写着昵称和抖音号，叫运营去百应「合作消息」看她说了什么、要不要加微信；变成 3「已拒绝」→ 弹「拒绝了」；99 / 100 / 101 → 弹「状态变了」。回了 / 拒了 / 不能沟通的以后不再查。一次最多弹 4 条，多的合成一条。
- 查不了（登录失效、掉登录、验证码、调试 Chrome 没开……）→ 弹「这次查不了」，两小时最多一次。
- 正在发卡（run 拿着台账锁）时这一轮跳过。
- 记录：`follow-state.json`（每位最后看到的状态、什么时候查的）、`follow.jsonl`（每次变化）、`follow.log`（每跑一轮一行：查了几位、谁变了、出了什么问题、为什么跳过），都在台账目录、0600。
- 没用百应的「待回复会话数」（`/connection/pc/im/conversations/all_unreply`）：2026-10-29 发了二十多张卡时它是 0 / 0，看来只算达人主动发起的会话。

## 放慢

两个命令行都不经 `bin/*.mjs` 直接跑，而是经本目录的两个包装（命令行的代码一行不改）：

- `paced-dy.mjs`：给抖音命令行页面传输的每个请求排队，等到离上一个平台请求（跨进程也算：台账目录的 `last-request` 记着时间）至少 `gap_seconds`。工具把 `DY_TRANSPORT` 去掉，保证走的是被放慢的页面传输。
- `paced-jst.mjs`：给聚水潭命令行换一个同样排队、放慢的 `fetch`。

每次运行的请求数记在 `work-…/requests.jsonl` 或 `run-…/requests.jsonl`（时间、方法、路径，不记参数、正文和应答）。
