## 二、对协议 v1 草案的意见

整体同意：Windows 主动开服务、Mac 来拉；事件流至少送达一次，加确认和去重；`send_id` 只发一次；`indeterminate` 不自动重发；单独的口令；只用相对时长。下面是要补的和要说清楚的。

### 要补的

1. **发出去但一直读不回来的，Windows 报一个事件。** 现在只有 `send_seen`。如果一直没读回，Mac 只能自己计时，而 Mac 不知道 Windows 那边的实际情况（比如微信卡住了）。建议读回窗口过了（文字 30 分钟、文件 10 分钟）还没对上，Windows 报 `send_unseen`，让 Mac 在控制台标"没确认发出"。
2. **Windows 自己出问题时报事件。** 比如微信掉线、弹出风控验证、读不了数据库、发送连续失败。建议加 `edge_status` 事件（`{"type": "edge_status", "wechat": "offline", "detail": "…"}`），Mac 控制台据此提醒运营。`/edge/health` 只在 Mac 来问的时候才知道，事件能留下记录。
3. **`/edge/health` 带上名单版本**，比如 `"parties_version": 3`。Windows 重装或者库丢了，Mac 发现版本对不上就重新推一次名单。
4. **`PUT /edge/parties` 的版本规则**：建议版本号比 Windows 现有的小或者相等时返回 409，避免旧的推送盖掉新的。Mac 是唯一写名单的一方。
5. **达人撤回消息。** 达人发了地址又撤回，Mac 上的草稿或审批单可能还在用这条。建议加 `creator_message_recalled`（带原 `message_id`）。现在做不到的话，先在协议里留这个类型，Windows 晚点再实现。
6. **引用回复。** 达人引用我们之前的某句话来回复时，建议 `creator_message` 带上 `quote`（被引用那句的文字），不然 Claude 看不懂"这个"指的是什么。
7. **其他消息类型**（名片、链接、视频、表情、位置等）：建议照样进事件流，`text` 写成 `[链接] 标题`、`[视频]` 这类占位文字，不要直接丢掉。丢掉的话，Mac 会以为达人没说话。
8. **发送前的等待。** 我们 Mac 端有"像真人打字"的等待：随机 2–6 秒，加上每个字 0.15 秒，最多 15 秒。这个由 Mac 自己控制（等够了再 `POST /edge/sends`），不用 Windows 管。和你们账号级的最小间隔、每小时上限叠加没有问题，只要 Windows 那边的上限能配置就行。夜间不主动发由 Mac 管，和你们的说法一致。

### 要说清楚的

9. **附件的确认顺序**：Mac 要先把附件下载好，再确认（ack）这条事件，对吗？确认后附件只再留 7 天。
10. **上传的文件留多久**：`POST /edge/uploads` 上传之后，如果一直没有发送请求用到它，多久删除？建议 24 小时。
11. **运营在手机上回的消息**：会同步到 Windows 的微信数据库吗？会的话，也按 `operator_message` 报吗？我们需要它也算"运营接手"。
12. **名单以外的私聊**：Windows 在"只收发"模式下，对不在名单里的私聊和群聊，照旧按现有配置交给机器人处理吗？我们这边之前的决定（D13）是：公司号上不在名单里的私聊照常聊天回复。协议里写一句，免得两边理解不一样。
13. **`/edge/events` 里的 `text` 是原文**：手机号不打码，对吗？我们 Mac 端在拼给 Claude 的提示之前换成占位符，写日志前也打码（我们仓库已有 `src/pii.py` 的 `mask_pii`）。Windows 侧的日志也请打码：我们仓库 10-25 已经把 router、wcdb_backend、decision_trace 写原文的地方都改成打码了，合并时请保留。

### 网络

14. **防火墙按你们的建议**：Windows 的 8790 只放行 Mac 的 IP，不放行整个网段。TLS 先不做，以后视情况再加。
