# 第 2 阶段第 6 项设计：审批入口和持久化（B4、B5）

> 状态：已实施（2026-10-25）。2026-10-24 用户对第 6 节的 Q1–Q4 回复"默认"，即按建议做。落实时的调整见第 8 节。
> 背景和路线护栏见 `handoff.md`；本文只讲这一项怎么做。

## 1. 要解决什么

- **B4 审批没有入口**：`execute_operator_approval` 没有任何地方调用，运营看不到审批单，也没法批。
- **B5 数据都在内存里**：审批单、申请草稿、白名单重启就丢。控制台（Web 服务）和机器人（`bot-main` 线程里的 router）虽然在同一个进程里，但控制台拿不到达人模块的对象；而且机器人停着的时候，达人模块的对象根本不存在，运营却应该照样能看审批单、维护名单。

## 2. 总体思路

- **数据库是唯一的数据来源。** 复用 `data/messages.db`（原项目已开启 WAL），新增 4 张以 `influencer_` 开头的表。建表代码放在新文件 `src/influencer/store.py` 里，不改原项目的 `src/db/schema.py`。
- **两边都只和数据库打交道。** 机器人这边（router → 达人模块）写草稿和审批单；控制台那边读审批单、执行审批。两边不共享内存对象。原项目的"群聊待办"也是这个做法：控制台接口直接打开数据库读写。
- **"只能执行一次"改用数据库的条件更新来保证。** 执行 `UPDATE ... SET status='EXECUTING' WHERE packet_id=? AND status='PENDING'`，只有更新到 1 行的那个请求才继续往下执行。现在靠的是线程锁，改用条件更新后，跨线程、跨进程、重启之后都能成立。
- **达人处理器由 `bot.py` 构造，再传给 router。** 现在是 router 在构造函数里自己建。改成打开数据库以后，router 的几百个测试用的都是默认配置（数据库路径是 `data/messages.db`），会把表建进真实的数据库文件里。改成由 `bot.py` 构造并传入，测试里不传就不会碰数据库。机器人启动时顺便把环境变量白名单并进名单（Q4）。

## 3. 数据表

| 表 | 用途 | 主要字段 |
|---|---|---|
| `influencer_contacts` | 达人白名单（D3）和达人档案 | `chat_id`（主键）、显示名、小红书账号、粉丝数、点赞数、数据更新时间、是否启用、备注、加入时间 |
| `influencer_drafts` | 还没补齐的申请（24 小时作废） | `chat_id`（主键）、草稿内容（JSON）、更新时间 |
| `influencer_approvals` | 审批单 | `packet_id`（主键）、`chat_id`、商品、SKU、库存、成本、收件人、电话、地址、小红书账号、资质标注、佣金、状态、失败原因、达人原话、创建 / 过期 / 处理时间、出库单号、运单号、佣金计划号 |
| `influencer_events` | 操作记录 | 审批单号、动作（创建 / 批准 / 驳回 / 失败 / 过期 / 补链接）、详情、来源（机器人 / 控制台）、时间 |

驳回原因记进 `influencer_events`，以后每周复盘时用得上（R7）。

## 4. 控制台

侧边栏新增"达人审批"，下面分两个子页。

**待审批**：每张审批单显示成一张卡片，内容如下。

- **达人**：昵称、`chat_id`、小红书账号（可以填写或修改）、资质标注（达标 / 不达标 / 待核实）
- **申请**：商品、SKU、库存、样品成本
- **收件**：姓名、电话、地址
- **达人原话**：作为证据（R5）
- **佣金**：默认 25%，可以往低改，上限 25%（D5）
- **批准后会发生什么**：在聚水潭建出库单，在小红书绑定 X% 的佣金
- **按钮**：通过 / 驳回。驳回时可以填写原因
- **结果**：成功时显示出库单号和运单号；失败时显示原因。"出库单已建、佣金绑定失败"这种情况要突出显示，提醒人工处理

页面顶部还有两项：
- 模拟模式打开时，显示一条醒目的横幅（D6）。
- 显示聚水潭、小红书 CLI 是否可用。

另外可以按"已执行 / 已驳回 / 失败 / 过期"筛选，方便事后追查。

**达人名单**：
- 列表，支持添加（`chat_id`、显示名、小红书账号）、启用和停用。
- 运营一般不知道达人的 `chat_id`，所以页面会列出"最近私聊过的联系人"（从消息表里取不以 `@chatroom` 结尾的会话），点一下就能设为达人。

## 5. 接口

接口写在 `src/web/server.py` 里。这是原项目的共享代码，改完要同步 `CODEBASE_REFERENCE.md`。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/influencer/approvals?status=pending` | 审批单列表 |
| POST | `/api/influencer/approvals/action` | 通过或驳回：`{packet_id, action, xhs_account?, commission_rate?, reason?}` |
| GET | `/api/influencer/contacts` | 达人名单 |
| POST | `/api/influencer/contacts/action` | 添加、修改、停用达人（单独用一个只收 POST 的路径，和 `/api/todos/action` 一样，GET 改不了数据） |
| GET | `/api/influencer/recent-chats` | 最近私聊过的联系人，供挑选达人 |
| GET | `/api/influencer/status` | 模拟模式是否打开、聚水潭和 CLI 是否就绪、待审批数量 |

安全措施沿用现有的三项：只监听 127.0.0.1、校验 Origin、POST 路径白名单。也就是说，只能在这台 Mac 上审批（D2）。

## 8. 落实时的调整（2026-10-25）

分 4 步提交：`b0543ed`（store.py）、`2ba1849`（处理器改为读写数据库）、`a44d2f9`（接口）、`22f2334`（页面）。和上面的设计相比，有这几处不同：

- 接口的具体处理放在 `src/influencer/console.py`，`src/web/server.py` 只负责转发（`_handle_influencer`）。这样对原项目共享代码的改动最小。
- 名单的写接口用 `/api/influencer/contacts/action`（只收 POST），不和读接口共用一个路径。
- 第一个子页叫「审批单」，不叫「待审批」：页面上可以按状态筛选，也能看已执行、已驳回的单。
- 达人处理器改由 `bot.py` 构造后传给 router（见第 2 节）。
- 驳回也给婉拒话术；到期清除个人信息时，连同姓名和达人原话一起清（见第 6 节）。
- 控制台点「通过」时，聚水潭和小红书 CLI 的调用就在这次请求里完成，页面会等结果。CLI 单次最多 30 秒。
- 执行到一半进程退出的单会一直停在"执行中"，页面只提示人工核对，没有做处理入口（handoff.md 的 B23）。
