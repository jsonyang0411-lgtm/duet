一、一页看懂（2026-10-26 晚）

整条线：在聚水潭找抖音、小红书达人 → 运营第一次联系、加微信 → 达人在微信里聊，Claude 起草回复、运营审过再发 → 收件信息和商品齐了生成审批单 → 运营批准后在聚水潭「寄样管理」建寄样单 → 专属佣金由运营在平台上另开。10-26 · 拍板 D31、D34

架构：微信登录在同事的 Windows 电脑上，只负责收发；Mac 上的服务处理消息，Claude 在受限的沙箱里起草回复，运营在 Mac 的控制台审核后，经 Windows 发出去。Mac 不登录微信。10-26 · 代码；Windows 端 · 告知

已经能用

  • 找达人：另一个 Claude（单独的工作目录 ~/daren-scout）用我们做的聚水潭命令行搜达人，按你定的标准列候选名单，运营确认后加进聚水潭达人库。第一轮加了 8 位抖音达人，全部读回确认成功。10-26 · 本机，真实账号

二、Claude 在系统里做什么、不做什么（替换原稿第一节）

分工：系统里有两个 Claude，都碰不到花钱或撤不回的动作。10-26 · 代码

  • 起草的 Claude：读业务资料和案卷，写回复草稿、建议合作单进哪个阶段。草稿由运营审了才发。
  • 找达人的 Claude：只能用聚水潭命令行的查询和"加达人"，不能发消息、建寄样单、开佣金。第一次联系达人由运营做。

建寄样单、开专属佣金、发消息，都只在运营批准以后由代码执行。

保证怎么做到的核实
起草的 Claude 不能执行命令、上网同事 worker 的沙箱：只有读写文件的工具，只能读业务资料目录、只能写案卷，没有外部工具10-26 · 代码、本机
起草的 Claude 看不到真实的电话和地址案卷里的号码是打码的，审批单生成时才换回真的10-26 · 测试
回复不经人审就发不出去每类回复一开始都要人审；近 20 条里 18 条原样通过才改成自动；钱、投诉永远人审10-26 · 代码（同事的 PRM）
达人在消息里写"忽略之前的规则"之类的话不管用达人的话只当聊天内容；就算 Claude 被带偏，草稿也要人审10-26 · 代码；模型实际抗干扰的效果未验证
佣金不会超过 25%写死在代码里，运营只能往低改10-26 · 测试
一张审批单只执行一次数据库里用条件更新占单，两个人同时点也只有一次10-25 · 测试
