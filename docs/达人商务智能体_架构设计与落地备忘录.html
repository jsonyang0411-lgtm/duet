二、为什么不让 Claude Code 直接当服务器（原稿第一节）

结论不变，代码也是这么做的：Claude Code 用来写代码；跑业务的是一个常驻在 Mac 上的 Python 服务，基础是开源的微信机器人 webot，达人模块挂在它的私聊入口上。10-24 · 代码

原稿的理由和技术细节，有两处要更正：

  • "Claude Code 调外部命令必须有人手动确认，非交互下直接报错"：这是同事实际碰到的情况，我们没有复现。告知，未验证不过，不管能不能配成免确认，业务都应该放在专门的常驻服务里：要 7×24 运行，每一步都要能测试，出了错要能追查。
  • "常驻服务（如 fastapi + anthropic SDK）直接调用 Claude API"：实际用的是 webot 自带的服务，基于 Python 标准库的 HTTP 服务，不是 fastapi。全局配置的大模型是 DeepSeek（AI_BACKEND=deepseek），不是 Claude。达人模块本身不调用任何大模型，全靠规则识别。10-25 · 本机 .env.macos、代码

  │  名单以外的私聊 → 原来的聊天流程

  ▼

四、5 个核心维度：原稿的决议和现在的事实（原稿第二节）

维度原稿写的现在的事实核实
1. 链路通信双向通信已打通；Win 本地转文字没有 Win ↔ Mac 链路，收发都在这台 Mac 上完成（mac_hybrid）。原项目有本地语音转文字（Whisper），默认关闭，没在这台 Mac 上用过10-25 · 代码、本机
2. 业务工具小红书 CLI + 聚水潭 ERP两个适配器都写好了。聚水潭真实接口没接（第 5 阶段），小红书 CLI 没交付。读操作可以自动调用；写操作（建单、绑佣金）只在审批通过后调用10-25 · 测试、代码
3. 资质裁决粉丝、点赞破千；不达标的自动回复"名额已满"改了：只在审批单上标"达标 / 不达标 / 待核实"，不自动拒绝；拿不到数据就标"待核实"，不编数字；数据明确不达标的，批准了也不寄样。门槛以代码为准：粉丝 ≥ 1 万且近期最高点赞 ≥ 1000（原稿写的是"破千"）10-25 · 测试；门槛 10-25 · 拍板
4. 审批闸门凡花钱必拦截；缺货、接口失败时自动通知运营拦截已实现：建单、绑佣金都要审批，达人模块的自动回复不做承诺。每张单只能执行一次，72 小时过期，批准时复查库存，佣金最高 25%。提醒只做在控制台里（D14）：缺货进「待处理」，执行失败记在审批单上，左栏显示数量；不推送到微信或飞书10-25 · 测试
5. 数据基座SQLite + WAL；以后可一键迁移到云端 Postgres已实现：达人数据存进机器人本来在用的 SQLite 文件（data/messages.db），WAL 由原项目开启。"一键迁移 Postgres"没做，也没验证10-25 · 测试、代码
